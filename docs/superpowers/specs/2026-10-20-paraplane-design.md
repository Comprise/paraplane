# paraplane — спецификация плагина Claude Code

Дата: 2026-10-20
Статус: черновик на согласовании

## 1. Цель

Плагин для Claude Code (бинарник на Go), который заставляет любой план реализации быть пригодным
для **параллельного исполнения субагентами без потери качества**:

- работа разбита на задачи с явным **владением файлами** (`owns`);
- задачи сгруппированы в **волны**: внутри волны задачи независимы и идут параллельно, волны — последовательно;
- порядок задаётся **зависимостями**, а не исходной нумерацией этапов: этапы можно переставлять,
  если так меньше конфликтов и короче план;
- каждая волна закрывается **gate** — полным прогоном проверок, поэтому следующая волна не ломает предыдущую.

Плагин только задаёт и проверяет правила; исполнять план — дело исполнителя (Claude сам,
`superpowers:subagent-driven-development` и т.п.). Правила исполнения (что передать субагенту,
когда стартует следующая волна) входят в skill `paraplane:rules`.

### Критерии успеха

- Любой план — из plan mode, `superpowers:writing-plans`, `/paraplane:create` или написанный вручную
  в файл плана — до начала исполнения содержит блок `paraplane` без ошибок валидации.
- В одной волне никакой файл (с учётом glob и «горячих» файлов) не меняют две задачи, и ни одна задача
  не читает файл, который в той же волне меняет другая.
- `paraplane check` сообщает, если раскладку можно сделать короче, и выводит её.
- Хук отвечает быстрее 1 с на плане из 100 задач, не пишет файлов в репозиторий и никогда не ломает сессию.

## 2. Принятые решения

| Вопрос | Решение |
|---|---|
| Какие планы ловить | Все: `ExitPlanMode` (plan mode), вызов skill с `plan` в имени, запись файлов планов, `/paraplane:create` |
| Исполнение | Только правила; собственного исполнителя нет |
| Изоляция субагентов | Владение файлами в общей рабочей копии (без worktree) |
| Как проверять план | Детерминированно, по машиночитаемому блоку `paraplane`; LLM — только в агенте-аудиторе |
| Скрытые конфликты (файлы, не названные в плане) | Агент `conflict-auditor`, запускается из skills, не из хуков |
| Реакция на нарушения | `ExitPlanMode` — запрет выхода (`mode: block`); файл плана — замечание Claude |
| Где активен | Везде, где установлен; выключается `enabled: false` в `.paraplane/config.yaml` |
| Состояние | Нет: плагин ничего не пишет в репозиторий; ошибки хуков — в stderr (видны в `claude --debug`) |
| Поставка | Как auto-context: шим `bin/paraplane` + бинарники `libexec/` из релиза |

## 3. Термины

- **План** — Markdown-документ; для paraplane значим только блок `paraplane`, остальное — для людей.
- **Задача** — единица работы одного субагента. **Волна** — набор задач, исполняемых одновременно.
- **`owns`** — пути и glob-шаблоны файлов, которые задача создаёт, меняет или удаляет. Только она.
- **`reads`** — пути, на содержимое которых задача опирается (интерфейсы, схемы), не меняя их.
- **Gate** — команда проверки, которую исполнитель запускает после волны; следующая волна стартует
  только при её успехе.
- **Горячий файл** — общий файл, который почти любая задача может задеть мимоходом
  (`go.mod`, lock-файлы, миграции); задан шаблонами `hot_files`.

## 4. Блок `paraplane`

Огороженный блок кода с info-строкой `paraplane` (бэктики или тильды, длина ограждения ≥ 3).
В плане ровно один такой блок. Содержимое — YAML:

```yaml
version: 1                  # необязательно; поддерживается только 1
gate: "go test ./..."       # необязательно; gate по умолчанию для волн плана
waves:
  - id: W1
    gate: "go vet ./... && go test ./..."   # необязательно; перекрывает gate плана
    tasks:
      - id: T1
        title: "Пакет config"
        owns: ["internal/config/**"]
        reads: []
        depends: []
        verify: "go test ./internal/config/"
      - id: T2
        title: "Пакет plan"
        owns: ["internal/plan/**"]
  - id: W2
    tasks:
      - id: T3
        title: "Валидатор"
        owns: ["internal/rules/**"]
        reads: [internal/plan/plan.go]
        depends: [T2]
```

- Неизвестные ключи — ошибка (опечатка в `depnds` не должна молча снимать зависимость).
- `id` — `[A-Za-z][A-Za-z0-9_.-]{0,31}`; задачи и волны в одном пространстве имён; `depends` на id волны —
  ошибка «unknown task».
- Пути — относительно корня проекта, разделитель `/`, без `..`, без ведущего `/` и `X:`, не `.`,
  нормализуются `path.Clean`. Glob — синтаксис `doublestar` (`*`, `**`, `?`, `[...]`, `{a,b}`);
  внутри `{}` и `[]` символ `/` запрещён, как и классы, способные совпасть с `/`: отрицание `[!…]`/`[^…]`
и диапазон `lo-hi` с `lo ≤ '/' ≤ hi` (иначе один сегмент шаблона мог бы покрыть несколько сегментов пути);
альтернатива `..` в `{}` (`{..,a}/x`) запрещена так же, как сегмент `..`.
- Литеральный путь — это файл. Каталог целиком пишется как `dir/**` (литерал, совпадающий с существующим
  каталогом, — замечание W5).
- **YAML:** каждый шаблон с любым из символов `* ? [ ] { } ,` или начинающийся с `!` или `&` пишется
  в кавычках (`"**/x.go"`): иначе YAML читает `*` как alias, `?` как ключ, `&` как якорь, а `[]{},` ломают
  список. Ошибка разбора с текстом `did not find expected alphabetic or numeric character` или
  `did not find expected ',' or ']'` сопровождается подсказкой `quote glob patterns`.
- Gate волны: `wave.gate` → `plan.gate` → `default_gate` из конфига → нет (ошибка E7).
- Лимиты (защита хука от враждебного плана): блок ≤ 256 КБ, ≤ 500 задач, ≤ 100 путей на задачу,
  ≤ 2000 путей (`owns` + `reads`) на план, шаблон ≤ 256 символов, ≤ 8 групп `{}` в шаблоне.
  Сравнение пар путей квадратично, поэтому общий лимит путей держит проверку обычного плана в пределах 1 с.
  Враждебный план (много групп `{}` подряд) может стоить doublestar экспоненциального перебора, поэтому
  хуки проверяют с дедлайном 5 с: не уложились — ошибка E0 `plan is too complex to check in time; simplify
  brace patterns or split the plan` (план не проходит непроверенным). CLI проверяет без дедлайна.

### 4.1. Пересечение шаблонов

Нужно консервативное «могут ли два шаблона описать один файл». `Overlap(a, b)`:

1. Оба литералы — равенство. Один литерал — `Match(шаблон, литерал)`.
2. Хотя бы один содержит подстроку `**` или `*` вплотную к `{`, `,` или `}` (с любой стороны: раскрытие `{…}`
   может склеить `**`, например `{*,a}*` совпадает с `p/q`) — пересечение, если статические префиксы (сегменты до первого
   с метасимволом) одного — префикс другого по сегментам.
3. Иначе (оба без `**` и без `*` у скобочной пунктуации; благодаря ограничениям `{}`/`[]` выше каждый сегмент шаблона покрывает ровно один
   сегмент пути): число сегментов должно совпадать, и каждая пара сегментов `s`, `t` должна «допускать
   общую строку»: литерал — `Match(другой, литерал)`; оба вида `*<lit>`, где `lit` без метасимволов, —
   один `lit` является окончанием другого (`*.go`/`*_test.go` да, `*.go`/`*.ts` нет); иначе — да.

Ложные срабатывания допустимы (сообщение говорит «may overlap» и советует сузить шаблоны),
пропуски — нет: если существует путь, совпадающий с обоими шаблонами, `Overlap` возвращает true.

### 4.2. Горячие файлы

Шаблон `hot_files` обозначает **общий ресурс** (`go.mod`, корневой lock-файл, каталог миграций).
Задача **задевает** горячий шаблон `H`, если в её `owns` есть `p`, для которого: `p == H`; или `p` литерал
и `Match(H, p)`; или `H` литерал и `Match(p, H)`. Широкий шаблон (`internal/**`) горячий файл не задевает:
чтобы менять `go.mod`, задача называет его явно. Ограничение: шаблон без `**` (`web/*.json`) горячий
шаблон не задевает — горячие файлы называют литеральным путём (это правило есть в skill `rules`). Две задачи одной волны, задевающие один `H`, — E5,
даже если это разные файлы (`migrations/0003_a.sql` и `migrations/0003_b.sql` конфликтуют по номеру).

## 5. Правила валидации

Каждое нарушение — строка с кодом, местом и текстом. Ошибки (E) делают план негодным, замечания (W) — нет.

| Код | Правило |
|---|---|
| E0 | Блок `paraplane` отсутствует, их больше одного, YAML не разбирается или превышен лимит |
| E1 | Структура: нет волн; пустая волна; нет `id`/`title`; повтор `id`; `depends` на неизвестную задачу; неверный путь или шаблон; неизвестный ключ или неверный тип; `version` не 1 |
| E2 | В одной волне `owns` двух задач пересекаются |
| E3 | `depends` указывает на задачу той же или более поздней волны (в т.ч. цикл) |
| E4 | В одной волне `reads` задачи пересекается с `owns` другой задачи |
| E5 | В одной волне две задачи задевают один горячий шаблон (п. 4.2) |
| E6 | Задача меняет то, что `owns` задачи более ранней волны, но не зависит от неё (прямо или транзитивно) |
| E7 | У волны нет gate |
| W1 | У задачи нет `verify` |
| W2 | В волне больше `max_parallel` задач |
| W3 | Раскладку можно сделать короче (п. 6) |
| W4 | У задачи пустой `owns` |
| W5 | Литерал в `owns` — существующий каталог (имелось в виду `dir/**`); только CLI и хуки, где есть ФС |

Порядок: E0 — остальное не проверяется. E1/E3 — проверяются только E7, W1, W2, W4, W5 (пересечения
и раскладка требуют целой структуры). Без E1/E3 — всё; W3 — только если ошибок нет вовсе.

E6 — главное правило «следующий этап не ломает предыдущий»: правка чужого результата допустима
только как осознанное продолжение (зависимость), тогда её исполнитель видит контракт предшественника.

### 5.1. Аудит волны (A1)

`paraplane audit <plan> <wave>` — проверка **после** исполнения волны и **до** её gate (артефакты gate —
покрытие, бинари — не попадают в аудит). Изменённые файлы рабочей копии
(`git status --porcelain=v1 -z --untracked-files=all`, для переименований — оба пути; пути приводятся
к корню проекта через `git rev-parse --show-prefix`, файлы вне корня отбрасываются) должны попадать в `owns`
какой-либо задачи этой волны; исключения — сам файл плана и шаблоны `audit_ignore`.
Нарушение — `error A1 W2: internal/x.go changed but no task of W2 owns it`.

Безопасность: `git status` может выполнить команду, заданную конфигом репозитория, а `paraplane audit`
одобряется хуком без запроса. Поэтому:
- перед `status` — `git config --show-scope --includes --get-regexp '^filter\..*\.(clean|smudge|process)$'`;
  любая строка из области `local` или `worktree` (включая подключённые через `include`/`includeIf`) —
  отказ `error: the repository config defines filter drivers; paraplane audit does not run git status here`
  (код 1); фильтры из `global`/`system` (например git-lfs) — доверенная настройка пользователя; «фильтров нет» —
  только код выхода 1 без вывода, любая другая ошибка — отказ;
- git запускается с `GIT_NO_LAZY_FETCH=1` (частичный клон не скачивает объекты через команды `remote.*`/`core.sshCommand`),
  `GIT_OPTIONAL_LOCKS=0` (индекс не пишется — хуки индекса не срабатывают), `-c core.fsmonitor=false`, без `GIT_DIR`,
  `GIT_CONFIG` и прочих переменных репозитория; `status` — с `--no-renames` и `--ignore-submodules=all`.
`git log` для прогресса фильтры не запускает.

Аудит опирается на правило исполнения «субагенты не коммитят, координатор коммитит после зелёного gate»:
тогда рабочая копия на момент аудита содержит ровно изменения текущей волны. Аудит не различает задачи
внутри волны (запись T1 в файл T2 не видна) — это ловят тесты gate; охрана в реальном времени — вне рамок.

## 6. Оптимальная раскладка (`--suggest`)

Считается только для плана без ошибок.

1. Отношение предшествования: все `depends`, плюс для каждой пары задач **разных** волн с конфликтом
   (пересечение `owns`, `reads`↔`owns`, общий горячий шаблон) — дуга от задачи более ранней волны.
   В плане без ошибок задачи одной волны не конфликтуют, а пересечение `owns` разных волн уже покрыто
   зависимостью (иначе E6).
2. Слои по длиннейшему пути (ASAP): задача без предшественников — в W1, иначе на слой после
   последнего предшественника. Это и есть перестановка этапов: независимый «третий» этап уходит в W1.
3. Все дуги идут вперёд по волнам автора, поэтому слоёв не больше, чем волн, а раскладка валидна по E2–E6.
   Слоёв меньше — замечание W3; `paraplane check --suggest` выводит раскладку готовым блоком
   `paraplane` (волны `W1…`, задачи без изменений). Gate слоя — действующий gate (`wave.gate` → `plan.gate`)
   самой поздней волны автора среди его задач; `plan.gate` пишется вверху блока, `gate` слоя — только если
   отличается. Слои не делятся по `max_parallel`: предложенная раскладка может давать W2.

## 7. CLI

```
paraplane check [--suggest] <file>   # проверить план; - читает stdin
paraplane audit <file> <wave>        # аудит изменений волны (п. 5.1)
paraplane progress <file>            # прогресс исполнения плана (п. 7.1)
paraplane hook <session-start|pre-tool-use|post-tool-use>
paraplane version
```

`check` печатает нарушения (`error E2 W1: T1 and T2 both own internal/a.go`), затем итог
(`plan ok: 3 waves, 7 tasks`, `plan ok with 2 warning(s): 3 waves, 7 tasks` или
`plan invalid: 2 error(s), 1 warning(s)`); с `--suggest` при W3 перед итогом — `Shorter layout:` и блок.
Код выхода: 0 — ошибок нет, 1 — есть ошибки или файл не читается, 2 — неверные аргументы. Проблемы
конфига — строки `warning: config: …` перед нарушениями. `audit` печатает нарушения A1 и итог
(`audit ok: W2, 5 changed file(s)` / `audit failed: 2 file(s) outside W2`); коды выхода те же;
нет git или не репозиторий, неизвестная волна, план с ошибками E — `error: …` и код 1.
Файл плана (кроме `-`) должен быть обычным файлом (не симлинк, не FIFO) внутри корня проекта, ≤ 1 МБ;
иначе `error: …` и код 1. Путь — относительно текущего каталога; для аудита приводится к корню.

### 7.1. Прогресс

Координатор коммитит каждую волну один раз, после зелёного gate, с трейлерами
`Paraplane-Plan: <путь плана от корня>` и `Paraplane-Wave: <id волны>`. `paraplane progress <file>`
читает блок и трейлеры коммитов текущей ветки и печатает состояние. Плагин не хранит состояния:
прогресс переживает перезапуск сессии. Цвет — эмодзи, т.к. ANSI в чате не рисуется.

Состояние волны по порядку плана: волна с коммитом, все предыдущие волны которой тоже `done`, — `done`
(gate прошёл); первая не `done` — `running`; остальные — `waiting`. Коммит волны, стоящей после `running`, —
строка `warning: wave <id> was committed before <running id>`; коммит волны, которой нет в плане, —
`warning: commit for unknown wave <id>`. Значения трейлеров, не подходящие под шаблон id, отбрасываются.

Пример (синтетический план `example.md`, 5 волн, 17 задач, выполнены W1 и W2):

```
paraplane · example.md                                    wave 3/5 · 64%
█████████████████████████░░░░░░░░░░░░░░░  11/17 tasks

W1  🟩🟩🟩🟩🟩🟩  6/6  ✓ done     T1 T2 T3 T4 T5 T6
W2  🟩🟩🟩🟩🟩    5/5  ✓ done     T7 T8 T9 T10 T11
W3  🟨🟨          0/2  ▶ running  T12 T13
W4  ⬜⬜          0/2  · waiting  T14 T15
W5  ⬜⬜          0/2  · waiting  T16 T17
```

Раскладка (ширина в колонках: 🟩 🟨 ⬜ — 2, остальные символы, включая `█ ░ ✓ ▶ ·`, — 1):
- Строка 1: `paraplane · <имя файла>` слева, `wave N/M · P%` справа, вместе ровно 72 колонки (имя
  обрезается `textx.Line`, чтобы уместиться). `N` — номер `running`; всё `done` — `wave M/M · 100%`.
  `P` = ⌊100·done/total⌋ по задачам `done`-волн.
- Строка 2: полоса из 40 символов, `█` = ⌊40·done/total⌋, остальное `░`, затем два пробела и `D/T tasks`.
- Пустая строка, затем по строке на волну: столбцы через два пробела — id (дополнен до самого длинного id),
  квадраты (🟩 done, 🟨 running, ⬜ waiting; ≤ 12, при большем числе — 12 и ` +N`; столбец дополнен до ширины
  самой широкой ячейки), `d/n` (дополнен до самого широкого), метка `✓ done` / `▶ running` / `· waiting`
  (дополнена до 9), id задач через пробел, обрезанные `…`, чтобы строка была ≤ 72 колонок. Хвостовые пробелы
  удаляются.
- Нет git или не репозиторий — `error: …`, код 1; репозиторий без коммитов — все волны по правилу выше;
  план с ошибками E — `error: …`, код 1.

Правило исполнения: после коммита каждой волны координатор запускает `paraplane progress <plan>` и
вставляет вывод в своё сообщение пользователю в блоке кода.

## 8. Хуки

Обработчики — чистые функции `(Env, Input) → []byte`; хук всегда выходит с 0; внутренняя ошибка
или паника — в stderr и пустой ответ (fail-open: ошибка плагина не мешает работе). Payload из stdin ≤ 4 МБ.
Корень — `CLAUDE_PROJECT_DIR`, иначе `cwd` из payload; далее ближайший каталог вверх с `.git`
или `.paraplane/config.yaml`. При `enabled: false` хуки молчат.

| Событие | Matcher | Что делает |
|---|---|---|
| `SessionStart` | — | `additionalContext`: одна строка о правилах и `paraplane:rules`; при проблемах конфига — `systemMessage` |
| `PreToolUse` | `ExitPlanMode` | проверяет `tool_input.plan` (пусто — читает `planFilePath`, ≤ 1 МБ; нет обоих — молчит); есть E (включая E0) — `permissionDecision: deny` и список нарушений (≤ 20) с инструкцией; только W — `additionalContext` |
| `PreToolUse` | `Skill` | имя skill не начинается с `paraplane:` и (без учёта регистра) содержит `execut` или `subagent-driven` — `additionalContext` с выжимкой **правил исполнения** и их приоритета над skill; иначе содержит `plan` — выжимка правил составления плана |
| `PreToolUse` | `Bash`, `if: Bash(paraplane *)` | авто-одобрение `paraplane check <путь>`, `paraplane audit <путь> <волна>`, `paraplane progress <путь>`, `paraplane version` (как в auto-context) |
| `PostToolUse` | `Write\|Edit` | `file_path` попадает в `plan_paths` — проверка файла (≤ 1 МБ), см. ниже |

PostToolUse не должен шуметь, пока план пишется и пока исполнитель отмечает чекбоксы:
- `Edit` проверяется, только если `old_string` или `new_string` содержит `paraplane` или ключ блока
  (`waves:`, `tasks:`, `id:`, `title:`, `owns:`, `reads:`, `depends:`, `verify:`, `gate:`), либо непустой
  `new_string` встречается (любое вхождение) внутри блока; `Write` — всегда.
- E0 — `additionalContext` (`add the block before the plan is final`), не блокировка.
- E1–E7 — `decision: block` + `reason`.
- Только W — `additionalContext`, и только для `Write`.

- `mode: warn` — вместо deny и `block` везде `additionalContext` с тем же текстом.
- Выжимка правил и тексты — английские константы в `internal/hooks`; skill `rules` повторяет их подробно.
- Текст из плана (id, пути, ошибки YAML) перед выводом очищается от управляющих символов и обрезается.

### 8.1. Факты Claude Code, требующие ручной проверки (Phase 7)

- Остаётся ли сессия в plan mode после `deny` хука на `ExitPlanMode` (документация не говорит).
  Запасной вариант, если нет: ответ `ask` с причиной, чтобы решение принял пользователь (правка `internal/hooks`).
- Имя поля skill в `tool_input` инструмента `Skill` не документировано: разбирать `skill`, затем `name`,
  затем `command`; проверить логом payload.
- Вызов `/skill` пользователем не проходит через PreToolUse — это ожидаемо, такие планы ловят
  `ExitPlanMode` и `PostToolUse`.

## 10. Skills и агент

| Компонент | Вызов | Назначение |
|---|---|---|
| `skills/rules` | Claude сам, `/paraplane:rules` | все правила: формат блока, E/W, как разбивать и переставлять этапы, правила исполнения; `references/` с форматом и примерами |
| `skills/create` | `/paraplane:create <задача или путь к спецификации>` | уточнить, изучить код, составить план, `conflict-auditor`, исправить, `paraplane check`, сохранить в `plans_dir/YYYY-MM-DD-<slug>.md` |
| `skills/check` | `/paraplane:check [путь]` | `paraplane check --suggest` + `conflict-auditor`, правка самого плана, отчёт о перестановках |
| `agents/conflict-auditor` | из skills; правило `rules`: при ≥ 2 задачах в волне | сверяет план с кодом: скрытые общие файлы, регистрационные точки, ломка API внутри волны, миграции; инструменты `Read, Grep, Glob`; модель `inherit` |

`create` и `check` — `disable-model-invocation: true` (меняют файлы по запросу пользователя).
Правила исполнения в `rules` **главнее указаний любого skill исполнения** (`superpowers:subagent-driven-development`, `executing-plans` и т.п.): для плана с блоком ` ```paraplane ` противоречащие указания («не запускай исполнителей параллельно», «исполнитель коммитит») не действуют. Промпт субагента содержит его `owns`, `reads` и `verify`; «не трогай файлы
вне `owns`; если нужно — остановись и сообщи»; задачи волны запускаются одним сообщением;
после волны — `paraplane audit <plan> <wave>`, затем gate; при нарушении аудита или красном gate —
исправление до старта следующей волны; **субагенты не коммитят** (параллельные коммиты гоняются за
`index.lock` и захватывают чужие файлы) — координатор коммитит один раз после зелёного gate волны
с трейлерами п. 7.1 и показывает `paraplane progress`.

Отчёт `conflict-auditor` — список `{kind: shared-file|hidden-write|api-break|order, tasks, file, evidence, fix}`
и вердикт `clean` / `conflicts`. План правит основной Claude.

### 12a.2. Поправки по шагу 0 (Codex 0.163, проверено 2026-10-20)

Эти факты главнее таблицы выше.
- **Plan Mode:** `permission_mode` остаётся `"default"`; `Stop` приходит, но `last_assistant_message` — `null`.
  План есть только в транскрипте (`transcript_path` из payload, JSONL): запись `type: "response_item"`,
  `payload.type: "message"`, `payload.role: "assistant"`, `content[].type: "output_text"` с текстом
  `<proposed_plan>\n…\n</proposed_plan>` (а также `event_msg` → `item_completed` с `item.type: "Plan"`), в рамках
  `turn_id` хода. Следующий запрос пользователя после кнопки реализации — `prompt: "Implement the plan."`.
  → `Stop` (Codex): транскрипт — обычный файл (Lstat), читается хвост ≤ 4 МБ; берётся последний
  `<proposed_plan>…</proposed_plan>` ассистента с этим `turn_id`; блок `paraplane` внутри проверяется; есть E —
  `{"decision":"block","reason":…}`; `stop_hook_active: true` — молчит; нет транскрипта/плана — молчит.
  Формат транскрипта не документирован: если хвост транскрипта читается, но в нём нет ни одной записи
  `response_item`/`message`, хук выдаёт `systemMessage` `paraplane: Codex transcript format not recognized; plan checks in
  Plan Mode are off (update paraplane)`, а не молчит. После каждого обновления Codex — живая проверка на плане с ошибкой.
- **Запись файлов:** Codex пишет файлы через `Bash` (`printf … > docs/plans/x.md`); `apply_patch` в проверке не
  встретился. `PostToolUse`: `tool_name: "Bash"`, `tool_input.command` — строка, `tool_response` — вывод.
  → `PostToolUse` (Codex, matcher `^(Bash|apply_patch)$`): из команды берутся слова-кандидаты (разбиение по пробелам
  и `;&|<>()`, снятие кавычек), относительные — от `cwd`; совпавшие с `plan_paths` существующие обычные файлы
  проверяются как в п. 8 (E1–E7 — `block`, E0 — контекст); для `apply_patch` — заголовки `*** Add/Update File:`,
  `*** Move to:`. Пропуск возможен (команда пишет файл косвенно) — его ловят `Stop` и skills.
- **`UserPromptSubmit`:** поле `prompt`; упоминание `$плагин:skill` видно текстом → дайджесты по п. 12a.
- **Агенты плагина Codex не загружает** (на просьбу запустить агента модель читала SKILL.md) → в Codex skills
  выполняют аудит сами по тексту `agents/conflict-auditor.md`.
- **Окружение хуков:** `CLAUDE_PLUGIN_ROOT` = `PLUGIN_ROOT` = каталог плагина в кеше Codex; `bin/` плагина в PATH нет;
  `cwd` — каталог сессии; `CLAUDE_PROJECT_DIR` не задан. Skill вызывается как `$плагин:имя`.
- Поля всех событий: `session_id`, `transcript_path`, `cwd`, `hook_event_name`, `model`, `permission_mode`;
  `turn_id` — у `UserPromptSubmit`, `PreToolUse`, `PostToolUse`, `Stop`; `tool_use_id` — у событий инструментов.
