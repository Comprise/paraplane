# Справочник paraplane

[English](reference.md) | **Русский**

Полный справочник: формат блока, правила, команды и их вывод, хуки, настройка, требования и ограничения. Начните с [README](../README.ru.md).

## Блок `paraplane`

В плане (Markdown) ровно один огороженный блок кода с info-строкой `paraplane`. Остальной текст плана — для
людей, paraplane его не читает. Содержимое — YAML:

````
```paraplane
version: 1                  # необязательно; поддерживается только 1
gate: "go test ./..."       # необязательно; gate по умолчанию для волн плана
waves:
  - id: W1
    gate: "go vet ./... && go test ./..."   # необязательно; перекрывает gate плана
    tasks:
      - id: T1
        title: "Пакет config"
        owns: ["internal/config/**"]
        reads: []
        depends: []
        verify: "go test ./internal/config/"
      - id: T2
        title: "Пакет plan"
        owns: ["internal/plan/**"]
  - id: W2
    tasks:
      - id: T3
        title: "Валидатор"
        owns: ["internal/rules/**"]
        reads: [internal/plan/plan.go]
        depends: [T2]
```
````

- **`owns`** — пути и glob-шаблоны файлов, которые задача создаёт, меняет или удаляет. Только она.
- **`reads`** — пути, на содержимое которых задача опирается (интерфейсы, схемы), не меняя их.
- **`depends`** — id задач более ранних волн; это зависимости, а не id волн.
- **`verify`** — команда проверки задачи; **`gate`** — команда, которую исполнитель запускает после волны.
  Gate волны: `wave.gate`, затем `plan.gate`, затем `default_gate` из конфига.
- Блок ограждается бэктиками или тильдами (длина ограждения не меньше 3). Неизвестные ключи — ошибка.
- Пути — от корня проекта, разделитель `/`, без `..` и ведущего `/`. Glob — синтаксис
  [doublestar](https://github.com/bmatcuk/doublestar) (`*`, `**`, `?`, `[...]`, `{a,b}`). Литеральный путь —
  это файл; каталог целиком пишется как `dir/**`.
- Шаблон с любым из символов `* ? [ ] { } ,` или начинающийся с `!` или `&` пишется в кавычках
  (`"**/x.go"`), иначе YAML разберёт его как alias, ключ или якорь. Если YAML не разбирается по этой причине,
  проверка подскажет `quote glob patterns`.
- Лимиты (защита хука от враждебного плана): блок ≤ 256 КБ, ≤ 500 задач, ≤ 100 путей на задачу, ≤ 2000 путей
  (`owns` + `reads`) на план, шаблон ≤ 256 символов (рун), ≤ 8 групп `{}` в шаблоне и ≤ 256 вариантов раскрытия групп `{}`
  (произведение числа альтернатив его групп `{}`).

## Правила проверки

Каждое нарушение — строка с кодом, местом и текстом. Ошибки (E) делают план негодным, замечания (W) — нет.

| Код | Правило |
|---|---|
| E0 | блока `paraplane` нет, их больше одного, YAML не разбирается или превышен лимит |
| E1 | структура: нет волн; пустая волна; нет `id`/`title`; повтор `id`; `depends` на неизвестную задачу; неверный путь или шаблон; неизвестный ключ или неверный тип; `version` не 1 |
| E2 | в одной волне `owns` двух задач пересекаются |
| E3 | `depends` указывает на задачу той же или более поздней волны (в том числе цикл) |
| E4 | в одной волне `reads` задачи пересекается с `owns` другой задачи |
| E5 | в одной волне две задачи задевают один горячий шаблон |
| E6 | задача меняет то, что `owns` задачи более ранней волны, но не зависит от неё (прямо или транзитивно) |
| E7 | у волны нет gate |
| W1 | у задачи нет `verify` |
| W2 | в волне больше `max_parallel` задач |
| W3 | раскладку можно сделать короче |
| W4 | у задачи пустой `owns` |
| W5 | литерал в `owns` — существующий каталог (имелось в виду `dir/**`) |
| A1 | только `paraplane audit`: изменённый файл волны не принадлежит ни одной её задаче |

- E6 — главное правило «следующий этап не ломает предыдущий»: правка чужого результата допустима только как
  осознанное продолжение (зависимость), тогда исполнитель видит контракт предшественника.
- **Горячие файлы** (`hot_files`) — общий ресурс (`go.mod`, lock-файлы, миграции). Задача задевает горячий
  шаблон, если называет подходящий файл явно; широкий шаблон (`internal/**`) горячий файл не задевает. Две
  задачи одной волны, задевающие один горячий шаблон, — E5, даже если это разные файлы
  (`migrations/0003_a.sql` и `migrations/0003_b.sql` конфликтуют по номеру).
- Пересечение шаблонов считается консервативно: возможны ложные срабатывания (сообщение «may overlap»),
  пропусков нет. Литеральные сегменты сравниваются без учёта регистра (`README.md` и `readme.md` в одной волне —
  «may overlap»: на macOS и Windows по умолчанию это один файл); горячие файлы сравниваются так же.
- Если есть ошибки E0, остальное не проверяется; при ошибках E1/E3 проверяются только E7, W1, W2, W4, W5;
  W3 выдаётся, только когда ошибок нет вовсе.

## Команды

В Claude Code:

| Команда | Что делает |
|---|---|
| `/paraplane:create <задача или путь к спецификации>` | уточнить задачу, изучить код, составить план, прогнать `conflict-auditor`, исправить, проверить `paraplane check` и сохранить в `plans_dir/YYYY-MM-DD-<slug>.md` |
| `/paraplane:check [путь]` | `paraplane check --suggest` плюс `conflict-auditor`, правка самого плана и отчёт о перестановках |
| `/paraplane:progress [путь]` | `paraplane progress` по запросу: исполняемый план или самый новый; закрытые незакоммиченные задачи сессии — в `--done`; вывод в блоке кода |
| `/paraplane:rules` | все правила: формат блока, E/W, как разбивать и переставлять этапы, правила исполнения (Claude подгружает его сам) |

`create`, `check` и `progress` вызывает только пользователь. Агент `conflict-auditor` запускается из
этих skills при двух и более задачах в волне и ищет то, чего нет в плане: скрытые общие файлы, регистрационные
точки, ломку API внутри волны, миграции. Его отчёт — список находок и вердикт `clean` или `conflicts`; план
правит основной Claude. Если план нельзя проверить (файл не читается, блоков `paraplane` ноль или несколько,
YAML невалиден, запрошенной волны нет в плане), вердикт — `error` с одной находкой `input`: это не `clean` — skill исправляет входные данные и
повторяет аудит или сообщает причину.

Консольная утилита (её можно запускать вручную; Claude пользуется ею сам):

```
paraplane check [--suggest] <file>   # проверить план; - читает stdin
paraplane audit <file> <wave>[,<wave>…]  # аудит изменений волны (или этапа из нескольких волн)
paraplane progress [--done <ids>] <file>  # прогресс исполнения; --done: закрытые незакоммиченные задачи
paraplane hook <session-start|pre-tool-use|post-tool-use> [--agent codex]
paraplane hook <stop|prompt-submit|permission-request> --agent codex   # события Codex — см. hooks/README.md
paraplane version
```

**Вне Claude Code.** `bin/` плагина лежит в PATH только у Bash-инструмента Claude Code. Из обычного
терминала запускайте `<каталог плагина>/bin/paraplane …` (в Claude Code — каталог в кеше плагинов, он же
`${CLAUDE_PLUGIN_ROOT}`; в Codex — каталог плагина в кеше Codex) или соберите бинарь из исходников:
`go build -o /usr/local/bin/paraplane ./cmd/paraplane` (нужен Go) и вызывайте как `paraplane`.

### `paraplane check`

Печатает нарушения, затем итог. Например, для двух задач одной волны с `owns` `internal/a.go` и `internal/*.go`:

```
error E2 W1: owns of T1 (internal/a.go) and T2 (internal/*.go) may overlap; narrow the patterns or move a task to another wave
warning W1 T1: task T1 has no verify
warning W1 T2: task T2 has no verify
plan invalid: 1 error(s), 2 warning(s)
```

Итоги: `plan ok: 3 waves, 7 tasks`, `plan ok with 2 warning(s): 3 waves, 7 tasks` или
`plan invalid: 1 error(s), 2 warning(s)`. С `--suggest` при W3 перед итогом выводится `Shorter layout:` и готовый
блок `paraplane` с более короткой раскладкой (независимый «третий» этап уходит в W1). Текст W3: ``warning W3: the layout can be shorter: 2 waves instead of 3 (`paraplane check --suggest` prints it)`` (при одной волне — `1 wave`). Код выхода: 0 — ошибок
нет, 1 — есть ошибки или файл не читается, 2 — неверные аргументы. Проблемы конфига — строки
`warning: config: …` перед нарушениями. Файл плана должен быть обычным файлом (не симлинк, не FIFO и не каталог:
`error: <путь> is a directory, not a plan file`) внутри корня проекта и не больше 1 МБ. Все строки `error:`,
`warning:` и итоги идут в stdout; в stderr — только текст usage (код выхода 2). Исключение — шим: если бинаря нет
или он не исполняемый, `bin/paraplane` печатает в stderr `paraplane: binary … was not found` (или
`… is not executable`) и выходит с кодом 1.

### `paraplane audit`

Проверка **после** исполнения волны и **до** её gate (артефакты gate — покрытие, бинари — в аудит не
попадают). Изменённые файлы рабочей копии должны попадать в `owns` какой-либо задачи этой волны; исключения —
сам файл плана и шаблоны `audit_ignore`. Проверяются и коммиты волны в текущей ветке: коммит задачи
(`Paraplane-Task`) может менять только файлы названных в нём задач
(`error A1 W2: x.go changed by T3 (commit abc1234) but T3 does not own it`), коммит волны или этапа — только файлы
названных волн (`… changed in commit abc1234 but no task of W1, W2 owns it`); итог тогда
`audit ok: W2, 5 changed file(s), 2 commit(s)`. Например, при двух посторонних файлах в рабочей копии:

```
error A1 W2: internal/x.go changed but no task of W2 owns it
error A1 W2: internal/y.go changed but no task of W2 owns it
audit failed: 2 file(s) outside W2
```

Успех — `audit ok: W2, 5 changed file(s)`. Нет git или не репозиторий, неизвестная волна, план с ошибками E —
`error: …` и код 1. Аудит опирается на правило исполнения «субагенты не коммитят, координатор коммитит после
зелёного gate»: тогда рабочая копия содержит ровно изменения текущей волны. Он не различает задачи внутри
волны — это ловят тесты gate.

**Безопасность аудита.** `git status` может выполнить команду, заданную конфигом репозитория, а
`paraplane audit` одобряется хуком без запроса, поэтому:

- перед `status` проверяются драйверы фильтров (`filter.*.clean|smudge|process`); любой, определённый в
  области `local`, `worktree` или любой другой, кроме `global` и `command` (включая подключённые через
  `include`/`includeIf`), — отказ
  `error: the repository config defines filter drivers; paraplane audit does not run git status here`
  (код 1). Доверенными считаются только фильтры из глобального (пользовательского) конфига git (например git-lfs); git
  запускается с `GIT_CONFIG_NOSYSTEM=1`, системный конфиг не читается вовсе. У git старше 2.26 нет `--show-scope`:
  тогда локальный конфиг и (если включён `extensions.worktreeConfig`) конфиг worktree запрашиваются отдельно, и
  любой фильтр в них — отказ;
- на git, который не учитывает `GIT_NO_LAZY_FETCH` (всё, кроме 2.46+ и исправлений 2.45.1, 2.44.1, 2.43.4, 2.42.2,
  2.41.1, 2.40.2, 2.39.4, а также версия, которую не удалось разобрать), `audit` отказывает с `error: … partial clone …`
  в частичном клоне (`extensions.partialClone` или `remote.*.promisor` задан в любой области) или если конфиг
  репозитория задаёт `remote.*.uploadpack`; обычные репозитории работают и на старом git;
- вывод git ограничен 16 MiB: больше (например, огромное дерево неотслеживаемых файлов) — отказ `git output too large`;
- каждый вызов git идёт с `GIT_NO_LAZY_FETCH=1`, `GIT_OPTIONAL_LOCKS=0` (индекс не пишется, хуки индекса не
  срабатывают) и `GIT_CONFIG_NOSYSTEM=1`, без `GIT_DIR`, `GIT_CONFIG` и прочих переменных репозитория, и с
  `-c core.fsmonitor=false -c core.pager=cat --no-pager -c log.showSignature=false -c gpg.program=false
  -c gpg.ssh.program=false -c gpg.x509.program=false -c core.hooksPath=/dev/null` (не запустятся пейджер,
  программы подписей и хуки);
- `status` — с `--no-renames` и `--ignore-submodules=all`, `git log` — с `--no-show-signature`.

### `paraplane progress`

Координатор коммитит каждую волну один раз, после зелёного gate, с трейлерами
`Paraplane-Plan: <путь плана от корня>` и `Paraplane-Wave: <id волны>`. `paraplane progress <file>` читает
блок и трейлеры коммитов текущей ветки. Плагин не хранит состояния, поэтому прогресс переживает перезапуск
сессии. Пример (план `example.md`, 5 волн, 17 задач, выполнены W1 и W2):

```
paraplane · example.md                                    wave 3/5 · 64%
█████████████████████████░░░░░░░░░░░░░░░  11/17 tasks

W1  🟩🟩🟩🟩🟩🟩  6/6  ✓ done     T1 T2 T3 T4 T5 T6
W2  🟩🟩🟩🟩🟩    5/5  ✓ done     T7 T8 T9 T10 T11
W3  🟨🟨          0/2  ▶ running  T12 T13
W4  ⬜⬜          0/2  · waiting  T14 T15
W5  ⬜⬜          0/2  · waiting  T16 T17
```

🟩 — волна выполнена, 🟨 — идёт, ⬜ — ждёт. Коммит волны, стоящей после идущей, даёт строку
`warning: wave <id> was committed before <running id>`; коммит волны, которой нет в плане, —
`warning: commit for unknown wave <id>`.

`--done T7,T9` (id через `,` без пробелов, перед файлом) перечисляет задачи, закрытые, но ещё не
закоммиченные. Волна закрыта, если у неё есть коммит или все её задачи в `--done`; закрытые задачи идущей
волны считаются выполненными и рисуются 🟩, поэтому бар движется до коммита волны. id, которого нет в плане,
даёт `warning: --done <id> is not a task of the plan`, задача ждущей волны —
`warning: --done <id> is in waiting wave <W>`; такие id не считаются. Пустой список, плохой id или флаг
дважды — ошибка аргументов (код 2). Передаются все закрытые и ещё не закоммиченные задачи всех незакоммиченных
волн (внутри этапа из нескольких волн — и более ранних).

Git читает трейлеры только из последнего абзаца сообщения коммита, поэтому `Paraplane-Plan` и
`Paraplane-Wave` ставятся туда вместе с `Co-Authored-By` и другими трейлерами, без пустой строки между ними.
Коммит, чьи строки `Paraplane-*` git не считает трейлерами, не засчитывает волну и даёт
`warning: wave <id> commit <hash>: trailers not in the last paragraph`; такой коммит нужно исправить (amend).
Один коммит может закрывать несколько волн (проект коммитит раз в этап): у него по трейлеру `Paraplane-Wave` на
каждую волну (подходит и `Paraplane-Wave: W1, W2`), и засчитываются все.

Задача сделана, если выполнено любое: её называет коммит (`Paraplane-Plan` и `Paraplane-Task: <id>`, можно
несколько в коммите); у её волны есть коммит; её субагент вернулся со строкой `Paraplane-Task: <план> <id>` в
промпте (хранится в `.git/paraplane/closed.json`, вне рабочего дерева; запись, сделанная до `git reset` на более
ранний коммит, больше не считается); она есть в `--done`. Волна сделана, если у неё есть коммит или сделаны все
её задачи. Закоммиченная задача ждущей волны даёт `warning: task <id> was committed before <running id>`;
строка задачи вне абзаца трейлеров — `warning: task <id> commit <hash>: trailers not in the last paragraph`.

В Claude Code хук `PostToolUse` сам показывает прогресс пользователю (`systemMessage`), когда возвращается
субагент или коммит называет план и с прошлого раза сделана волна (при `progress: task` — задача); модели
сказано его не повторять. Когда координатор показывает прогресс, задаёт ключ `progress`: `wave` (по умолчанию) — после каждой
закрытой волны (аудит и gate прошли), `task` — ещё и после каждой закрытой задачи. Вывод всегда идёт
пользователю в блоке кода. Сам пользователь может запросить его в любой момент командой `/paraplane:progress`.

## Правила исполнения

Skill `paraplane:rules` главнее указаний любого skill исполнения (`superpowers:subagent-driven-development`,
`executing-plans` и т.п.): для плана с блоком `paraplane` противоречащие указания («не запускай исполнителей
параллельно», «исполнитель коммитит») не действуют.

1. Промпт субагента содержит его `owns`, `reads` и `verify`; «не трогай файлы вне `owns`; если нужно —
   остановись и сообщи».
2. Задачи волны запускаются одним сообщением.
3. После волны — `paraplane audit <plan> <wave>`, затем gate. При нарушении аудита или красном gate — исправление
   до старта следующей волны.
4. Субагенты не коммитят (параллельные коммиты гоняются за `index.lock` и захватывают чужие файлы): координатор
   коммитит один раз после зелёного gate волны с трейлерами `Paraplane-Plan` и `Paraplane-Wave`.
   Только если правила самого проекта требуют один коммит на этап из нескольких волн, координатор коммитит раз
   в этап: после каждой волны аудит идёт сразу по всем волнам этапа (`paraplane audit <plan> W1,W2`), а коммит
   этапа перечисляет все его волны, по трейлеру `Paraplane-Wave` на каждую.
5. Прогресс показывается после каждой закрытой волны, а при `progress: task` — ещё и после каждой закрытой задачи.

## Хуки

Хуки ловят план в любом виде: из plan mode, из skill с `plan` в имени, из файла в `plan_paths`.

| Событие | Что делает |
|---|---|
| `SessionStart` | добавляет в контекст строку о правилах и `paraplane:rules`; при проблемах конфига — сообщение |
| `PreToolUse` `ExitPlanMode` | проверяет план; есть ошибки E (включая E0) — **запрещает выход из plan mode** и перечисляет нарушения (до 20) с инструкцией; только замечания W — добавляет их в контекст |
| `PreToolUse` `Skill` | перед skill исполнения (имя содержит `execut` или `subagent-driven`, не начинается с `paraplane:`) напоминает правила исполнения и их приоритет; перед skill с `plan` в имени — правила составления плана |
| `PreToolUse` `Bash` | одобряет без запроса `paraplane check <путь>`, `paraplane audit <путь> <волна>[,<волна>…]`, `paraplane progress [--done <ids>] <путь>`, `paraplane version` |
| `SubagentStop`, `Stop` | субагент закончил (в том числе фоновый): строки `Paraplane-Task` из промпта в его транскрипте записываются; в конце хода `Stop` показывает прогресс пользователю (`systemMessage`) |
| `PostToolUse` `Bash\|Agent\|Task` | вернувшийся субагент со строкой `Paraplane-Task: <план> <id>` в промпте или коммит, называющий план: если с прошлого раза сделана волна (`progress: task` — задача), показывает прогресс пользователю (`systemMessage`) |
| `PostToolUse` `Write\|Edit` | если файл входит в `plan_paths` — проверяет его (≤ 1 МБ). E0 — только подсказка `add the block before the plan is final`; E1–E7 — **блокировка** с причиной; только W — подсказка, и только для `Write` |

- `Edit` проверяется, только если правка касается блока `paraplane` или его ключей (`waves:`, `tasks:`, `id:`,
  `title:`, `owns:`, `reads:`, `depends:`, `verify:`, `gate:`) либо новый текст встречается внутри блока: пока
  исполнитель отмечает чекбоксы, хук молчит.
- Хуки всегда выходят с кодом 0 и ничего не пишут в репозиторий. Ошибка плагина уходит в stderr (видна в
  `claude --debug`), ответ пустой: плагин не мешает работе (fail-open).
- Проверка в хуке ограничена 5 секундами; не уложились — ошибка E0
  `plan is too complex to check in time; simplify brace patterns or split the plan`. CLI проверяет без дедлайна.
- `mode: warn` в конфиге заменяет запрет и блокировку на сообщение с тем же текстом.
- Подробнее — [`hooks/README.ru.md`](../hooks/README.ru.md).

## Настройка

Конфиг необязателен и лежит в `.paraplane/config.yaml`; все поля необязательны. Неизвестный ключ или неверное
значение — предупреждение, остальные поля применяются.

| Поле | По умолчанию | Смысл |
|---|---|---|
| `enabled` | `true` | выключить плагин в проекте |
| `mode` | `block` | `block` или `warn`: блокируют ли хуки (`ExitPlanMode`, PostToolUse) или только сообщают |
| `plan_paths` | `docs/plans/**/*.md`, `docs/superpowers/plans/**/*.md`, `.paraplane/plans/**/*.md` | какие файлы — планы |
| `hot_files` | `go.mod`, `go.sum`, `**/package.json`, `**/package-lock.json`, `**/pnpm-lock.yaml`, `**/yarn.lock`, `**/Cargo.toml`, `**/Cargo.lock`, `**/pyproject.toml`, `**/uv.lock`, `**/poetry.lock`, `**/migrations/**` | горячие файлы |
| `default_gate` | `""` | gate по умолчанию; одна строка не длиннее лимита, без управляющих символов (включая TAB, NUL, ESC, DEL), U+2028/U+2029 и невидимых форматирующих символов (категория Cf), иначе игнорируется с предупреждением |
| `max_parallel` | `6` | порог W2, 1…32 |
| `plans_dir` | `docs/plans` | куда `/paraplane:create` сохраняет планы; относительный путь без `..` и без символов глобов `* ? [ ] { }`, иначе игнорируется с предупреждением |
| `audit_ignore` | `[]` | шаблоны файлов, которые аудит не учитывает (генерируемое, кеши) |
| `progress` | `wave` | когда координатор показывает прогресс: `wave` — после каждой закрытой волны; `task` — ещё и после каждой закрытой задачи |

Корень проекта — `CLAUDE_PROJECT_DIR`, иначе `cwd` сессии; далее ближайший каталог вверх с `.git` или
`.paraplane/config.yaml`.

## Требования

- Claude Code (CLI, расширение для IDE или desktop-приложение) или Codex CLI (см. «Codex CLI»).
- Linux, macOS или Windows (amd64 или arm64). Go не нужен: плагин ставится с готовыми бинарниками.
- `git` — нужен для `paraplane audit` и `paraplane progress`; проверка плана (`check`) и хуки работают без него.
  - `audit` проверен с git 2.18. В частичном клоне он отказывает, если git не учитывает `GIT_NO_LAZY_FETCH`: нужен
    2.46+ или 2.45.1, 2.44.1, 2.43.4, 2.42.2, 2.41.1, 2.40.2, 2.39.4. Git из дистрибутива, где исправление
    перенесено под старым номером версии (например, 2.34.1 в Ubuntu), считается старым, поэтому там `audit` в
    частичных клонах отказывает: обновите git или используйте полный клон.
  - `progress` требует git 2.22+ (трейлеры читаются через `%(trailers:key=…)`); на более старом — явная ошибка.
  - Вывод git больше 16 MiB (например, огромное дерево неотслеживаемых файлов) — `audit` отказывает с
    `git output too large`.
- **Windows:** нужен [Git for Windows](https://git-scm.com/downloads/win) — без Git Bash хуки плагина
  не запускаются. Если Git Bash стоит не в стандартном месте, укажите путь в `settings.json`:

  ```json
  { "env": { "CLAUDE_CODE_GIT_BASH_PATH": "C:\\Program Files\\Git\\bin\\bash.exe" } }
  ```

## Codex CLI

Те же правила и тот же бинарь; отличается способ доставки.

В терминале:

```
codex plugin marketplace add Comprise/paraplane --ref release
```

Затем в Codex: `/plugins` — установить `paraplane`; `/hooks` — **доверить** хуки плагина (пока они не
доверены, Codex их не запускает).

- Skills вызываются как `$paraplane:rules`, `$paraplane:create <задача>`, `$paraplane:check [путь]`.
- `bin/` плагина не в PATH shell-инструмента Codex: тексты хуков называют CLI абсолютным путём
  `<каталог плагина>/bin/paraplane`, skills берут команду оттуда. Хуки Codex — `hooks/codex.json`,
  вызов `paraplane hook <событие> --agent codex`.
- Агентов плагина Codex не загружает: skills выполняют аудит сами по тексту `agents/conflict-auditor.md`.

| Что | Claude Code | Codex |
|---|---|---|
| План из plan mode | `PreToolUse` `ExitPlanMode`: запрет выхода | `Stop`: план из блока `<proposed_plan>` в транскрипте; есть E — `block`, Codex продолжает ход и правит план; повторный `Stop` того же хода молчит |
| Файл плана | `PostToolUse` `Write\|Edit` | `PostToolUse` `^(Bash\|apply_patch)$`: файлы из команды `Bash` (`printf … > файл`) и заголовков патча; E1–E7 в файле, который команда пишет, — `block`, в файле, который она только читает (`cat plan.md`), — только контекст; запись косвенной командой возможна мимо хука — ловят `Stop` и skills |
| Правила перед skill | `PreToolUse` `Skill` | `UserPromptSubmit`: промпт упоминает `$…` с `execut`/`subagent-driven` или `plan` |
| Одобрение CLI | `PreToolUse` `Bash` | `PermissionRequest` `^Bash$`, только строгая форма команды и абсолютный путь CLI |
| Контекст сессии | `SessionStart` | `SessionStart` (со ссылкой на `$paraplane:rules`) |
| Агент `conflict-auditor` | запускается из skills | не загружается; аудит выполняет сам Claude по тексту агента |

`mode: warn` и `enabled: false` действуют так же. Подробности хуков — [`hooks/README.ru.md`](../hooks/README.ru.md).

## Ограничения

- Исполнение планов, запуск субагентов и worktree — вне рамок: плагин только задаёт и проверяет правила.
- Запрет записи вне `owns` во время исполнения не реализован (хук не знает, какой субагент пишет): сейчас
  есть только аудит после волны.
- Аудит не различает задачи внутри волны: запись одной задачи в файл другой ловят тесты gate.
- Скрытые конфликты (файлы, не названные в плане) детерминированная проверка не видит — для этого агент
  `conflict-auditor`, который запускается из skills, а не из хуков.
- Хуки не используют LLM.
- Пересечение и горячие файлы сравниваются без учёта регистра; `audit` (A1) сопоставляет изменённые пути с `owns`
  точно, с учётом регистра. Unicode-нормализации нет: на macOS написания одного имени в NFC и NFD — один файл, но
  разные пути для проверки, поэтому их пересечение не обнаруживается (описано в skill `rules`).
- Codex: возврат плана через `Stop` в Plan Mode (`decision: block`) вживую не проверен (Codex избежал конфликта
  сам); проверять после обновлений Codex (спецификация, раздел 13).
- Вызов `/skill` пользователем не проходит через `PreToolUse`; такие планы ловят `ExitPlanMode` и `PostToolUse`.
- Остаётся ли сессия в plan mode после запрета выхода, документация Claude Code не уточняет; поведение
  проверяется вручную.

## Если что-то не работает

- В `/hooks` должны быть хуки плагина: `SessionStart`, `PreToolUse`, `PostToolUse` (в Codex — `SessionStart`, `UserPromptSubmit`, `PostToolUse`, `Stop`, `PermissionRequest`, и они должны быть доверены).
- `paraplane check <план>` покажет предупреждения конфига (`warning: config: …`) и нарушения плана.
- Ошибки хуков пишутся в stderr: запустите `claude --debug`.

## Разработка

```sh
make test                                    # тесты
make dist                                    # бинарники для 6 платформ в libexec/ (нужно перед --plugin-dir)
make tree DIR=/tmp/paraplane-tree            # поставляемое дерево: ровно пути из ship.txt
claude --plugin-dir /path/to/paraplane       # запустить Claude Code с локальной версией
```

Без `make dist` шим `bin/paraplane` не находит бинарь в `libexec/` (см. `bin/README.ru.md`).

- `.gitattributes` принудительно задаёт переводы строк LF, поэтому на Windows при checkout и установке POSIX-шим
  остаётся рабочим; файл тоже поставляется.
- `ship.txt` — единый список поставляемых путей. `make tree DIR=<каталог>` собирает по нему дерево (пропуская
  `libexec`, если его нет); строгая проверка в CI, tar-архив релиза и ветка `release` читают один и тот же файл.
- CI гоняет `go test` на трёх платформах, отдельное задание `go test -race ./...` на ubuntu и проверку плагина;
  изменения в `docs/` тоже запускают CI.
- Релиз — тег `vX.Y.Z` на коммите из `main`: workflow соберёт бинарники и обновит ветку `release`, из которой
  ставится плагин. Версия бинаря без префикса `v` (`paraplane version` для тега `v0.9.1` печатает `0.9.1`). Перед
  публикацией релиз прогоняет бинарь и шим: оба должны напечатать версию тега.
- Спецификация (на русском):
  [`docs/superpowers/specs/2026-10-20-paraplane-design.md`](https://github.com/Comprise/paraplane/blob/main/docs/superpowers/specs/2026-10-20-paraplane-design.md).
