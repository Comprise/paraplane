# internal/track
Сводит коммиты, состояние и `--done` в готовый прогресс плана и счётчики сделанного.

## Назначение
- Одно место, где решается, что сделано в плане (спека 2026-10-23 §4): коммиты волн, этапов и задач, задачи вернувшихся субагентов из состояния, `--done`. Через него прогресс рисуют и CLI (`paraplane progress`), и хук прогресса.

## Публичный API / точки входа
- `PlanHash(md) string` — hex SHA-256 тела блока ```paraplane (`plan.Extract`); без единственного блока — `""`.
- `PlanRef{Rel, Hash, Plan}` — план для отчёта: путь от корня, хеш блока, разобранный план.
- `Statuses(ctx, root, plans, st state.State) (Result, error)` — прогресс планов; `st` не меняет. Один `gitx.Scan` (инкрементально от `st.Scan`), один `gitx.Unreachable` на головы всех записей. `Result{ByPlan map[string]Status; Apply func(*state.State)}`: `Apply` хук вызывает внутри `state.UpdateCtx` на заново прочитанном состоянии — ставит `Scan` (новый кеш скана) и чистит записи. Git в `Apply` нет; он безопасен на состоянии, прочитанном позже `st`: добавленные тем временем записи остаются, если их не убирает то же правило.
- Правило чистки: удаляются только (а) записи задач, сделанных коммитом (коммит задачи или её волны; хеш блока не важен; голова записи достижима) и (б) записи текущего блока (тот же `PlanHash`), чьей задачи нет в плане. Записи с недостижимой головой или другим `PlanHash` просто не считаются и остаются: возврат на ветку или откат текста плана возвращает их; старые вытесняет лимит 4096. Записи планов не из `plans` не трогаются.
- `PlanStatusContext(ctx, root, planRel, p, planHash, extra) (Status, error)` — то же для одного плана с `--done` (`extra`); состояние только читает (кеш скана тоже), никогда не пишет.
- `PlanStatus(root, planRel, p, extra)` — устаревшая обёртка: `context.Background()` и пустой `planHash` (совпадает с записями без хеша, которые пишет нынешний хук). R13 удаляет.
- `Status{Text, Waves, Tasks}`: вывод `progress.RenderFrom` с предупреждениями о потерянных трейлерах в конце (`warning: wave|task <id> commit <hash>: trailers not in the last paragraph`), счётчики из `progress.Count` (одно правило «сделано»).

## Структура и поток данных
- `compute`: `loadCache(st.Scan)` → `scan(ctx, root, from)` → `unreachable(ctx, root, головы записей + from, HEAD)`. Если `from` достижим из `HEAD`, скан был инкрементальным: коммиты = кеш ∪ новые (без повторов по хешу); иначе (переписанная история) — только новый полный скан.
- Для каждого плана `gitx.CommitsOf` → `judge`: запись считается, если `Plan` и `PlanHash` совпадают, голова достижима и задача есть в плане. Записи идут в `progress.Input.Recorded` (своё предупреждение `warning: task <id> finished before <running id>`), `--done` — в `Closed`.
- `keep` для `State.Prune` строится в том же проходе из уже сделанного скана; записи, добавленные позже, проверяются тем же правилом.
- `scan` и `unreachable` — переменные пакета (`gitx.Scan`, `gitx.Unreachable`), тесты считают вызовы и подменяют ошибки.

## Инварианты и подводные камни
- Ошибки git и чтения состояния возвращаются одинаково (L13); молча пропускается только состояние другой версии (`state.ErrVersion`). Не репозиторий — ошибка `GitDirContext`. При ошибке `Result` пуст, писать нечего.
- Кеш скана недоверенный: любой коммит с неполным хешем, пустым планом, неверным id или без id выбрасывает весь кеш (полный скан). Кеш больше 1 МиБ JSON не хранится (`Apply` ставит `Scan = nil`), чтобы `closed.json` не перерос лимит чтения 4 МиБ.
- Репозиторий без коммитов: скан пуст, кеш `nil`, записи недостижимы и не считаются, но остаются.
- После `git reset`, `--amend`, rebase или переключения ветки записи с недостижимой головой не считаются, но не удаляются (отступление от буквы спеки §5 по решению координатора R9).
- Старые записи с пустым `PlanHash` (их пишет хук до R10) в `Statuses` и `PlanStatusContext` с настоящим хешем никогда не считаются; удаляются они только чисткой по коммиту (с достижимой головой) или лимитом 4096. Считает их лишь устаревшая обёртка `PlanStatus` (пустой хеш), до R13.
- Запись сделанной коммитом задачи удаляется, только если её голова проверена и достижима: запись с другой ветки, где задача не закоммичена, переживает визит на эту ветку; головы, не проверенные в этом вызове (записи, добавленные после чтения `st`), не удаляются по этому правилу.
- Кеш скана хранит результаты разбора трейлеров `gitx` (`gitx.TrailerCommit`), а не сырые коммиты: изменение разбора трейлеров в `gitx` требует поднять версию состояния или иначе сбросить кеш. `maxCache` — переменная пакета (1 МиБ), тесты её понижают.
- Из нескольких `PlanRef` с одинаковым `Rel` берётся первый, остальные игнорируются.
- Изменение текста блока плана меняет `PlanHash` — записи старого блока перестают считаться, но остаются до отката текста или вытеснения лимитом.
